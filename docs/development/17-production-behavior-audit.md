## 1. 从实际写入回查制作和设置入口

审计从扣料、发布产物、创建余料实体和保存配置查回入口，再看失败值是否真的中止写入、失效标记是否被消费。普通 C、双击部分合成、详情确认和显式单目标回退都收敛到 `CraftingService` 私有提交链及 `CraftingTransaction.execute`。扫描、审阅和提交前分别覆盖不同的时间窗口，期间材料、权限和规则都可能变化。

| 路径 | 实际消费的条件与结果 |
| --- | --- |
| 普通 C、双击部分合成 | 网络先限制频率及共享额度，将工作交给主线程。服务端再查模式、菜单及单调序号。普通 C 只尝试完整计划。双击读取同菜单、同配方、时限内的前次服务端缺料结果，首次成功、重放、未知或截断都不能开启部分准备。 |
| 搜索、完整见证、详情确认 | `restrictRequest` 将世界规则和个人收紧写入实际搜索、容量和提交请求。见证只提供完整路线，审阅要重新发现来源并查真实配方、贡献、返还物和联合容量。确认前先消费一次性令牌，再按当前菜单、维度、规则、世代和收支重建，摘要改变就重新审阅。完整失败之外的未知或只读诊断不授予部分执行。 |
| 多件和 MAX | 本地数量与 MAX 走同一规划核心，保留未知和已证实的下界。选择固定数量后仍需审阅与确认。容量可能随数量增加而改善，骨粉回归实际覆盖一份失败、两份腾出槽位可做，选择数量时零消耗。世界步数上限、帧长、表示和计算额度分别约束，MAX 投影也占公平调度片。 |
| 扣料、产物与余料实体 | 提取后的数量、组件、交付失败和实体发布结果都影响事务终态。失败先清本次可安全撤回的实体，再恢复受影响来源前像。提交后再通知，观察者异常只记录，已交付的材料不退回。第三方回调对其它世界状态的任意写入不在补偿范围。 |
| 原版菜单操作 | `AmbientInventoryMenu` 在原版点击、配方放置和转移前检查 `stillValid`。失效时关闭或退出，正常网格和光标返还仍走原版生命周期。部分合成白名单只用于本模组的显式部分意图。 |
| 配置写入 | 普通页在延迟滑块提交前后复查上下文，草稿通过注册校验才保存改项。子名单完成只合回父草稿，取消不落盘。专业页在实际标量、名单、Undo/Redo、Reset 和退出保存边界复查世界身份。远程设置请求只读取值。 |

状态由产生和消费它的模块一起管理。`CraftingSessions` 保存连接序号、前次服务端结果、短期令牌和不透明来源绑定，菜单变化只清派生状态，保留连接的重放水位。`FailureEvidence` 确认资源、空位、访问与规则仍匹配后可在 40 tick 内复用服务端自产的充分失败，后续仍用当前诊断和执行检查。诊断命令可用环境短缓存，审阅和制作使用新鲜扫描。

`BrowseSnapshotTransfers` 管传输数据和轮转，`ClientBrowsePlanner` 与结果库管客户端任务、缓存证据和累计额度。资源、规则、配方世代、菜单及连接更新时各自释放旧状态。同值续租可复用数学结果，旧显示与见证不能穿过新授权。取消详情会退役待发点击和迟到回复，已经发送的服务端请求仍独立裁定。磁盘配方知识只保存可重建的静态关系，异步写回接收不可变值并按世代拒绝旧结果。

## 2. 清理结果与测试边界

- **收拢同职责的代码。** 浏览传输从包处理器移到包内 `BrowseSnapshotTransfers`，保留原准入和清理顺序。快照解码游标改为具名状态，网络字段顺序和限额保持原样。搜索与见证共用有效策略，见证入口仍拒绝部分意图。派生状态与求解清理分别复用，保留序号、完整失败证据和累计预算的不同寿命。移除重复的缓存估算、插入模拟的中间转换及证实不可达的界面分支。
- **删除已退出玩家路径的包装。** 服务端旧预览批次和 MAX 门面、专用缓存/进度、冷重试、测试便捷合成，以及 `invalidate` 的空壳和无效序号分配退出。真实客户端仍用 `Maximum` 值记录，服务端仍用 `FailureEvidence`。旧权限、容量和材料变化反例迁到真实审阅/确认，设置测试优先用注册草稿。事件、Mixin、注册工厂和网络处理器按框架实际入口核对，显式诊断保留。
- **让测试失败说明风险。** 客户端与跨进程知识夹具统一进 `src/integrationTest`，发布 JAR 排除该源集，服务端 GameTest 仍由 NeoForge 发现。设置、规划和背包主流程使用具名步骤和分工明确的场景，重复世界操作放入包内测试辅助。界面断言以注册值、控件身份、翻译参数和真实字体边界为准，守恒、权限和有界长度仍精确核对。清理失败不盖过原断言，过期截图或配置回调不应恢复已关闭状态。
- **让通过范围可追溯。** 本地从 `tests/run.ps1` 分组，CI 使用 Gradle `build`。运行器核对本次退出码、日志身份和完成标记，过滤及显式诊断单列。知识重启需先保存，再独立启动验证同份缓存确实载入且首次查找命中。测试整理中曾有未归因的材料换位、预览预算拒绝和批量确认超时，分别保留在[验收记录](18-pre-m5-acceptance.md)。容量夹具发现邻近结构进入扫描范围后只缩小隔离夹具的扫描半径，未改产品预算或断言。
- **补齐同处中英说明。** 解释求解、预算、缓存、事务、线程和界面失效边界，测试说明反例为什么需要特定输入、时钟和观察时机。注释批次以整理后的工作树为基线，175 份 Java 的非注释 token 一致，PowerShell 和 Gradle 也核对了同类边界。行为修复与纯注释批次分别留证，后续约定见[开发指南](../developer-guide.zh-CN.md#code-comments)。

## 3. 个人余料偏好热改

原详情只追踪部分合成模式，个人 TOML 热改“允许丢出余料”时，已打开页面仍可能沿用旧 `allowDrops` 和审阅令牌。本地新规划已收紧，但旧操作仍可用，服务端的世界规则检查一直生效。修复让详情同时比较余料偏好并更新意图，退役旧草稿、MAX、待发点击和显示见证。恢复先前偏好也不能复活旧回复。已发送的确认仍由服务端按原规则裁定。

真实客户端先取得服务端令牌，再翻转注册偏好并触发原按钮。修复前 `20261022-151703-910-planning` 失败于旧确认意图仍活动。修复后场景等待自然重算，再完成原有确认和库存核对。该场景通过注册值验证状态失效，人工另测文件监听和掉落实体。

10-28 在普通 `runClient` 中完成两项人工补验。两次均在世界允许余料掉落、主产物能装入但余料必须掉落的条件下操作。

1. 保持详情打开，在客户端 TOML 禁止掉落并等待实际文件重载，再点击原按钮。确认旧方案不会提交，材料与地面物品保持不变。
2. 恢复个人偏好。确认旧令牌没有自动恢复，重新审阅并明确点击后才制作一次。

`logs/client-M5-Pre-3.log` 有四次客户端配置文件重载和正常结束记录，逐项交互结果来自游玩回报。又没有独立测试 JAR 哈希。专业页跨世界和快照停滞是另外两项，本次人工未能构造，将它们留给下节的自动化验收。

## 4. 生命周期缺陷与独立反例

### 专业页失效写回

世界或连接改变后，旧专业页原先仍可能通过原生标量、延迟滑块或捕获的 Undo/Redo/Reset 回调写值。旧父导航还可能为未访问子页重新取得身份。修复把校验放到实际写点和退出保存处，限制子页继承原导航树身份。逐帧禁用说明当前状态，合法改值继续使用 NeoForge 的即时注册值、撤销和保存机制。旧专业页反例 `20261023-101848-947-settings` 实际写错 `horizontalRadius`，修复后的设置专项拒绝旧写入。

隔离客户端中，页面先合法改布尔和数值并产生 Undo，然后保持页面打开，通过原版方法实际开放 LAN。后续实际断线，等待 SERVER spec 卸载，再创建并进入第二个世界。重放旧控件、Undo/Reset、导航与退出均未修改旧世界或新世界的注册值与 TOML。`20261023-194237-737-settings` 通过。该轮先消去一次被拒滑块操作生成的历史项，确保真正命中此前合法的 Undo。世界、连接和时钟均取自游戏，另一台机器实际加入 LAN 的边界仍未覆盖。

### 浏览快照停滞和关闭

原接收器有一次重试的组件测试，但玩家停滞后丢弃接收器，服务端对同一内容只续租。修复让现有 `BrowseRequest` 用非零会话和 `resources=-1` 表达缺内容，同订阅与当前快照最多补传一次。同内容的新头沿用首次总期限，真正的资源版本替换先释放旧数据再建立新身份。轮转、准入、并发、内存和计算额度沿原约束。关闭、摘要失败或总期限耗尽后不能复活。临时关闭补传分支时，真实请求/轮询反例 `20261023-102500-373-planning` 在等待补传处失败。

隔离客户端在真实 Netty 管线暂扣约 800 KB 快照的 26 块，头、心跳和租期照常通过。停滞 5601 ms 期间双方各推进 139 tick，既有心跳触发一次补传并正确解码，资源身份未变。随后关闭真实菜单，再放行旧块，20 tick 内旧接收器和快照均未恢复，归还材料并重开后新菜单正常就绪。首轮 `20261023-193021-936-planning` 继续全组时在后续 MAX 压力处失败，另一次 `20261023-193929-777-planning` 只跑停滞专项并标 `FILTERED_STALL_ONLY`。该证据验证受控传输和取消，实际公网断连、自然丢包与任意负载未覆盖。

### 确认迟到和反例敏感性

真实按键收到的 `CONFIRMATION_REQUIRED` 曾在关闭原菜单后向新配方书页弹出旧详情。`LateConfirmationScenario` 在 Netty 暂扣并放行实际回复，旧版 `20261023-202417-606-inventory` 捕获跨页误弹，客户端与服务端始终只有一原木，没有成品或材料消耗。详情仍只读，提交继续要求新审阅和令牌。更早因同 tick 节流和 hover 丢失导致的两轮夹具失败只能说明未取得有效触发。

修复只保留最新普通 C 的展示归属。收到相同序号后消费记录，再核对配方、页面、菜单、世界和连接。关闭或显式打开详情、模式或会话清理都会退役记录。`20261023-202840-903-inventory` 通过，跨页旧回复不会弹出，同页仍自动打开，两个场景都不取料。

四份同源码测试副本分别运行完整 server 组。对照的 155 项全通过，各反例只临时改变一个生产条件，断言、额度和测试入口保持相同。补上 ACTIVE 反例时把断言放在观察者捕获边界外，重入使用新序号，避免在序号校验提前退出而测不到防重入。

| 临时变异 | 失败和证据 |
| --- | --- |
| 跳过一次性令牌消费 | 5 项真实失败，旧令牌在准入耗尽后重放实际得到 `CREATED`。 |
| 跳过世界规则收紧 | 4 项真实失败，原应禁用的部分执行变成 `CONFIRMATION_REQUIRED`，四态组合和旧审阅失效反例报错。 |
| 忽略 ACTIVE 防重入拒绝 | 1 项真实失败，新序号嵌套请求原应节流，实际进入规划并得到 `MISSING_INGREDIENTS`。 |

这些是三条独立反例的证据。对照、三份补丁和日志见 `run/verification/20261023-evidence-strengthening/` 的 `mutations/README.md`，其基线早于网络迟到提示修复。上述专业页和传输场景经游玩确认属于自动化或受控验收，10-28 未作为人工通过项，也不再阻塞阶段收口。

## 5. MAX 信号的归因和编译警告

10-23 停滞隔离运行随后在压力场景报 `MAX slice blinked the confirm button`。原现场未记录失败时的租期、ready 或草稿来源，且失败早于后续续期注入。10-24 的对照能说明旧断言遗漏了授权前提，仍无法确定原现场的唯一原因。

| 隔离对照 | 实际观测 |
| --- | --- |
| 自然重放 `20261024-003144-203-planning` | 原断言和完整规划组通过一次。 |
| 对齐到真实 MAX 等待 `20261024-003813-178-planning` | 自然出现本地完整草稿及 MAX 等待后，先见新鲜授权时按钮可点，再见同一作用域、租期过期且 `NO_TOKEN` 时按钮变灰，旧断言因错误要求可点而失败。 |
| 初版双向断言 `20261024-004302-721-planning` | LOW 压力夹具在 NORMAL 控件更新后退役作用域，LOWEST 观测到授权已换而界面尚未消费的中间态。生产拥有者下一次 tick 退役旧草稿，实际提交仍独立复验。 |
| 续期对照 `20261024-005007-771-planning` | 同一作用域实测可点、过期变灰、续期恢复。之后隐藏工作压力断言仍失败，只有过期 8 tick 内 `hiddenWhileExpired=0` 的观测，没有起点剩余任务量，该轮完整规划未通过。 |

后决定，主树只修测试。新鲜授权和同一作用域下的过期分支都要验证，前者可点、后者变灰。跨作用域仍由生命周期和排队取消反例约束。产品 MAX、授权、预算与调度未变，隐藏工作压力断言保留。四批日志与停在何处见 `run/verification/20261024-warning-and-max/max-README.md`。

编辑器警告按项目的固定依赖和解析器处理。Gradle 的布尔续行换兼容 Groovy-Eclipse 的写法，保留短路顺序，仓库 `url` 改显式赋值。缓冲区构造显式保留旧构造的 `ConnectionType.OTHER` 编码上下文。NightConfig 使用 `entrySet()` 和原始值，给专业页的 Map 继续保留顺序、注册值身份和只读性。已加载区块查询和注册物品 holder 使用等价接口，图控件迁到带鼠标键的回调，保留左键、焦点和绘制边界。清理未用导入，反射列表按实际元素类型验证。javac、ECJ 分别检查三源集，最终目标警告均为零。一次与 Gradle 重建并行执行的 ECJ 因依赖类型解析失败，顺序重跑才取得成功证据。
